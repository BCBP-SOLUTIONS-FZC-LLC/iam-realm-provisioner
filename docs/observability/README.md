# Enterprise Platform Observability Standard — iam-realm-provisioner

How this service implements the standard defined and enforced by [platform-gincommon](https://github.com/BCBP-SOLUTIONS-FZC-LLC/platform-gincommon/tree/main/docs/observability) (its `docs/observability/`, shipped with each release). This page covers what is specific to iam-realm-provisioner; the standard itself, its rules and the governance process are documented there. The layout mirrors [iam-org-membership's](https://github.com/BCBP-SOLUTIONS-FZC-LLC/iam-org-membership/tree/main/docs/observability).

| Piece | Location |
|---|---|
| Metric inventory (every metric this service emits, by tier) | [`metric-registry.md`](metric-registry.md), generated by `make metrics-inventory` |

| Compliance checks in CI | `.github/scripts/metricslint.sh`, `check-metric-naming.sh`, `metrics-registry-lint.sh` |
| Alerts, recording rules, SLOs | `deploy/monitoring/app-alerts.yml`, `slo-rules.yml`, `deploy/helm/templates/prometheusrule.yaml` |
| HPA | `deploy/helm/templates/hpa.yaml`, `deploy/monitoring/prometheus-adapter-rule.yaml` |

## Platform libraries

| Library | Version | Emits here | Wiring |
|---|---|---|---|
| platform-gincommon | v1.6.0 | `platform_http_*`, `platform_build_info`, `platform_library_info{library="platform-gincommon"}`; owns the registry and `metricslint` | `gincommon.ObservabilityMiddlewares(cfg)` in `internal/adapter/inbound/http/router.go`, with `Config.RequestTimeout` (30s) as the innermost handler; `/metrics` served by `gincommon.MetricsHandler()` on `METRICS_PORT` |
| platform-events/v2 | v2.0.0 | `platform_messages_*`, `platform_retry_total`, `platform_dlq_messages_total`, `platform_dlq_depth`, `platform_queue_depth`, `platform_duplicate_messages_total` (inbox), `platform_outbox_*`, `platform_dependency_request_seconds` (SNS/SQS/codec), `platform_event_propagation_seconds`, ... | `events.InitMetrics(events.MetricsIdentityFromLabels(gincommon.MetricsConstLabels()), gincommon.MetricsRegisterer())` |
| platform-pgcommon/v2 | v2.0.0 | `platform_db_*`, labelled `pool="default"` (app pool) and `pool="system"` (BYPASSRLS pool — reconciler sweeps, gauge exporters, the AL-5 audit drainer, RP-13) | `pgmetrics.InitWithIdentity(pgmetrics.IdentityFromLabels(...), gincommon.MetricsRegisterer())`, before `pgcommon.NewPool` |

All three register on `gincommon.MetricsRegisterer()`, so one scrape serves every collector. Order in both binaries: `ObservabilityMiddlewares` (fixes the identity) → `metrics.Register` (builds this service's collectors, including `platform_dependency_request_seconds`, which platform-events then adopts) → `events.InitMetrics` → `pgmetrics.InitWithIdentity` → pools. `TestStandard_LibrariesShareRegistryCollectors` (`internal/adapter/outbound/metrics/standard_test.go`) pins that order: no library metric may be disabled, and platform-events must adopt the shared histogram rather than be refused.

Traces use the same identity: `gincommon.InitTracingWithConfig` (server and reconciler), `db.query` spans from `gincommon.NewSpanTracer`, consumer spans from `gincommon.NewTracer` (`internal/adapter/inbound/sqspipeline`), and Keycloak spans named `keycloak.<op>`. `OTEL_EXPORTER_OTLP_ENDPOINT=none` (or `OTEL_TRACES_EXPORTER=none`) turns export off without losing trace IDs.

## Identity

| Label | Value | Source |
|---|---|---|
| `domain` | `iam` | `observabilityDomain` (`cmd/*/identity.go`); Helm also sets `OBSERVABILITY_DOMAIN=iam` |
| `service` | `iam-realm-provisioner` | `APP_NAME`, default `iam-realm-provisioner`, in **both** binaries |
| `environment` | `local`, `dev`, `test`, `staging` or `prod` | `resolveAppEnv()`: `APP_ENV`, else `ENVIRONMENT`, else `dev`; passed explicitly to metrics, tracing and logging so they cannot disagree. Anything else (e.g. `production`) fails startup |
| `version` | build version | `BUILD_VERSION`; only on `platform_build_info` |

The reconciler CronJobs share the server's identity, because the standard requires `iam_realm_provisioner_*` series to carry `service="iam-realm-provisioner"`. A run is identified by the `cronjob` grouping label of its push and by its `reconciler.<job>` span. CronJobs are never scraped: each run pushes its metrics to `PROMETHEUS_PUSHGATEWAY_URL` (`cmd/reconciler/main.go`, `pushMetrics`). **With that URL empty, every reconciler counter — and the alerts on `trial_expiry_deferred_total` and `realm_export_total` — stays dark.** Each run is a fresh process, so a pushed counter is that run's own count and stays until the next run replaces it. The reconciler alerts therefore read the pushed value, selected by `service` and the `cronjob` grouping label (`increase()` over a once-a-day step never held). This requires the Pushgateway scrape to use `honor_labels: true`, and the NetworkPolicy to allow egress to `networkPolicy.pushgatewayPort`.

## Tiers in this service

| Tier | Namespace | Built by | Count |
|---|---|---|---|
| 1 — platform-shared | `platform_*` | The libraries. This service builds exactly one itself: `platform_dependency_request_seconds`, from its registry entry (`gincommon.NewSharedHistogramVec`), because it records every Keycloak Admin API call into it (`dependency="keycloak"`); platform-events adopts the same collector for SNS/SQS/codec | see [inventory](metric-registry.md) |
| 2 — IAM domain-shared | `iam_*` | — | 0 |
| 3 — service-specific | `iam_realm_provisioner_*` (frozen prefix, LLD §25) | `prometheus.New*` with gincommon's const labels, registered on `gincommon.MetricsRegisterer()` (`metrics.Register`) | 26 |

**Why no Tier 2.** RP-INV-1 makes this service the only Keycloak Admin API caller in the platform, so nearly everything it measures is a behaviour no other IAM service has. Two registry entries do overlap and are open decisions (see [Items awaiting ratification](#items-awaiting-ratification)): `iam_rls_violations_total` (this service's RLS counter is the Tier 3 `iam_realm_provisioner_rls_violations_total`) and `iam_realm_operations_total` (ownerless; this service's realm operations are on Tier 3 counters such as `provision_total`).

Label **values** stay bounded:

- `platform_dependency_request_seconds{dependency="keycloak"}`: `operation` is the frozen §25 Keycloak op name (`create_realm`, `token`, ...); `outcome` ∈ `success`, `error`.
- `iam_realm_provisioner_rls_violations_total{violation_type}` ∈ `cross_tenant_access`, `missing_or_invalid_guc` (both pre-initialised to 0).
- `iam_realm_provisioner_unknown_event_acknowledged_total{topic}` is one of the three source topics (`iam.membership.events`, `iam.tenant.events`, `billing.events`), never a queue URL.
- `consumer` labels are the frozen `processed_events.consumer` values (`membership`, `tenant`, `billing`).
- `result`/`outcome`/`action`/`trigger`/`status` labels use fixed vocabularies listed in each metric's help text.

No metric carries a high-cardinality label (`tenant_id`, `user_id`, `event_id`, `realm`, ...).

### Proposed Tier 1 metrics and their Tier 3 counterparts

`platform_dependency_request_seconds` and `platform_duplicate_messages_total` are `proposed` in the registry. Until they are ratified, the Tier 3 counterparts recorded for the same events are the authoritative alerting and SLO source:

| Proposed | Authoritative until ratified |
|---|---|
| `platform_dependency_request_seconds{dependency="keycloak"}` | `iam_realm_provisioner_keycloak_call_duration_seconds`, `iam_realm_provisioner_keycloak_call_failures_total` (SLO-2, `IAMRealmProvisionerKeycloakCallFailureRate`) |
| `platform_duplicate_messages_total` | `iam_realm_provisioner_processed_events_duplicates_total` |

Where no Tier 3 counterpart exists (`platform_http_*` for the error-rate and latency alerts and SLO-1, `platform_dependency_request_seconds{dependency="sqs"}` for receive errors), the alert reads the proposed metric and carries `metric_status: proposed`. `metrics-registry-lint.sh` fails CI if that label is missing — or present on an alert that reads only approved metrics.

### Who counts what (no double counting)

- `platform_dlq_messages_total` is counted **only** by platform-events, once per forward (`operation="consume"`: `max_receive_count` on the 5th failed delivery, `malformed`, `decode_error`, or `explicit` for `sqspipeline`'s straight-to-DLQ schema-violation route; `operation="outbox_publish"`: `max_attempts`). Why a consumed message was rejected is on `iam_realm_provisioner_consumed_schema_violations_total{consumer,event_type}`.
- `platform_duplicate_messages_total` is counted by platform-events' inbox (`pkg/inbox`, which this service dedups through); the service counts only the Tier 3 `iam_realm_provisioner_processed_events_duplicates_total{consumer}`.
- `platform_messages_{received,processed,failed}_total` are counted by the SQS consumer; the service never records them.
- Keycloak calls are recorded once per call, on both `iam_realm_provisioner_keycloak_call_*` (Tier 3) and `platform_dependency_request_seconds{dependency="keycloak"}` (Tier 1) from the same instrumentation point (`internal/adapter/outbound/keycloak/instrumentation.go`). Both are expected; dashboards should pick one.
- `platform_http_request_timeouts_total` is counted by gincommon's timeout middleware.

## Adding a metric

1. Decide the tier with the standard's decision tree. A new `platform_*` or `iam_*` metric is a registry PR to platform-gincommon, never a local definition.
2. Tier 3: add the collector to `registerMetrics` in `metrics.go` as `iam_realm_provisioner_<name>`: `_total` (counter), `_seconds` (histogram) or no suffix (gauge), snake_case labels, no `*_id`/`email`/`ip` labels, `ConstLabels: gincommonLabels()`, and add it to the `MustRegister` list. Names are frozen once released (LLD §25).
3. Record one representative sample in `exerciseEveryCollector` (`metrics/standard_test.go`) so `metricslint` validates its labels, and add it to `TestNamingConvention_ConformsToPlatformObservabilityStandard`'s pre-warm list.
4. Run `make metrics-inventory` and commit the regenerated [`metric-registry.md`](metric-registry.md).
5. If it backs an alert, add the alert's `runbook` annotation (`docs/observability/runbooks.md#<alert-name-lowercase>`) and the entry in [`runbooks.md`](runbooks.md).

| Check | Where | What it enforces |
|---|---|---|
| `check-metric-naming.sh` (`make metric-naming-lint`) | `validate-quality.yml` | Every registered collector follows the tier prefixes, suffixes, label rules and registry vocabularies (`TestNamingConvention_*`, via `pkg/obsregistry`) |
| `metricslint.sh` (`make metrics-lint`) | `validate-quality.yml` | platform-gincommon's `metricslint check` on a real scrape (registry compliance, label vocabulary, cardinality), with `-allow-proposed-owner platform-gincommon,platform-events,platform-pgcommon`; `metricslint refs deploy docs` (no removed or unregistered names); [`metric-registry.md`](metric-registry.md) matches the code |
| `metrics-registry-lint.sh` (`make metrics-registry-lint`) | `validate-test.yml` | No removed name in any rule, HPA or adapter file; every alert on a proposed metric carries `metric_status: proposed` (`TestMonitoring_*`) |
| `TestStandard_LibrariesShareRegistryCollectors` | unit tests | Production registration order; platform-events adopts the shared histogram; `version` appears only on `platform_build_info` |

`metricslint check -strict` would fail today on every `proposed` entry without an allowed owner.

## Items awaiting ratification

Proposed registry entries this service depends on, or overlaps with:

- **`platform_dependency_request_seconds`** — this service is one of its emitters (`dependency="keycloak"`). Its governance note records the `{target_service,endpoint}` vs `{dependency,operation,outcome}` conflict across IAM services; this service uses the registry shape. Tier 3 Keycloak metrics stay authoritative until it is ratified.
- **`platform_duplicate_messages_total`** — emitted by platform-events' inbox here; Tier 3 counterpart above.
- **`iam_rls_violations_total`** (Tier 2, no owner) — emitted by iam-org-membership, iam-audit-log and iam-user-profile with the same `rls_violation_log` scrape this service feeds into `iam_realm_provisioner_rls_violations_total`. Adopting it would mean emitting the Tier 2 name alongside the frozen Tier 3 one and moving the two RLS alerts once it is ratified — a decision for the IAM owner, not taken unilaterally here.
- **`iam_realm_operations_total`** (Tier 2, no owner, no label vocabulary) — "administrative realm operations". This service is the only realm administrator (RP-INV-1), so if it is ratified it most likely belongs here; its label set needs agreeing first.
- **The libraries' own metrics** (`platform_http_*`, `platform_build_info`, `platform_outbox_*`, `platform_db_*`, `platform_queue_depth`, `platform_dlq_depth`, ...) — owned by the libraries; allowed via `-allow-proposed-owner`.

## Platform-library and audit-delivery alerts

The `iam_realm_provisioner_platform_libraries` group, ported from iam-org-membership: `IAMRealmProvisionerOutboxBacklog` (`platform_outbox_oldest_pending_age`), `DLQBacklog` (`platform_dlq_depth`), `ConsumerDead`, `DBPoolSaturated`, `DBAcquireErrors`, `DBRetriesExhausted` (all `metric_status: proposed`), and `AuditEntriesRejected` / `AuditEntriesUndelivered` (Tier 3 `audit_entry_backlog_gauge`). `ConsumerDead` deliberately differs from O&M's. It fires when the consumers stop *polling* (`receive_message` calls stop), not when a queue goes quiet: this service's queues, Billing's especially, are legitimately silent for long periods.

## SLOs

Recording rules and burn-rate alerts in `deploy/monitoring/slo-rules.yml`:

| SLO | SLI (recording rule) | Target | Alerts |
|---|---|---|---|
| SLO-1 write-path availability | `iam:realm_provisioner_write_error_rate:ratio_rate_5m`: `status_class="5xx"` share of `POST\|PUT\|PATCH\|DELETE` in `platform_http_requests_total` (intentional 4xx such as `idp_region_portability_failed` excluded) | 99.5% | `IAMSLO1_RealmProvisionerWriteErrorFastBurn` (14.4×, page), `IAMSLO1_RealmProvisionerWriteErrorSlowBurn` (6×, ticket) |
| SLO-2 Keycloak Admin API success | `iam:realm_provisioner_keycloak_success_ratio:rate_{5m,1h}` from the Tier 3 Keycloak pair | 99% | `IAMSLO2_RealmProvisionerKeycloakFastBurn` (page), `IAMSLO2_RealmProvisionerKeycloakSlowBurn` (ticket) |
| SLO-3 reconciler convergence | `iam:realm_provisioner_reconciler_markers:sum` = `realm_config_pending_gauge` + 1h increase of `trial_expiry_deferred_total` | markers ≤ 5 | `IAMSLO3_RealmProvisionerReconcilerMarkersElevated` |

Every SLI keeps `domain`, `service` and `environment`.

## HPA

CPU and memory are the primary HPA signals. `deploy/monitoring/prometheus-adapter-rule.yaml` exposes `platform_http_requests_per_second` (from `platform_http_requests_total`) as the optional RPS-per-replica input; because that metric is still proposed, `hpa.yaml` carries `observability.platform/metric-status: proposed`. `platform_queue_depth` (platform-events, sampled every `SQS_QUEUE_DEPTH_INTERVAL`, 60s by default) is the natural queue-based signal once ratified; it is not used yet.
