# CLAUDE.md

This file provides guidance to Claude Code when working with the **Realm Provisioner Service** (`iam-realm-provisioner`), a Go microservice in the IAM subsystem (Tender Management SaaS platform). Refines the IAM HLD; LLD v1.21 Approved (`docs/lld/iam-lld-realm-provisioner-service.md`), owner database `provisioner` on shared RDS PostgreSQL. Where LLD and HLD disagree, HLD is authoritative.

## What This Repo Is

`iam-realm-provisioner` is a **private Go service** (module: `github.com/BCBP-SOLUTIONS-FZC-LLC/iam-realm-provisioner`) that is the **single writer to the Keycloak Admin API** (RP-INV-1) and the system of record for tenant identity lifecycle in the IAM platform. It provisions and tears down Keycloak realms and users, migrates trial tenants into dedicated realms, configures per-tenant SAML/OIDC identity providers (secrets held only in OpenBao, never Postgres), and drives the tenant lifecycle state machine (trial → active → suspended → offboarded) via seven scheduled reconciler jobs. Org & Membership owns the organizational/business model and calls this service over the mesh; this service owns Keycloak realm/user/IdP *administration* and the small amount of local state needed to make that administration safe, idempotent, and replayable.

**Key responsibilities (sole writer for):**
- **`tenant_realms`** — one row per tenant: realm name/strategy (`shared`|`dedicated`), Keycloak shard, lifecycle status (`provisioning`|`active`|`disabled`|`suspended`|`exported`|`deleted`), trial/conversion/disable/export timestamps, `record_version`.
- **`keycloak_idp_configs`** — per-tenant SAML/OIDC IdP configuration, **non-secret** params only; the secret itself lives exclusively in OpenBao.
- **`keycloak_idp_config_validations`** — append-only §11.6 region-portability validation run history + admin acknowledgements.
- **`realm_config_reconciliations`** — RP-C4's retry ledger for realm-config settings that failed to apply inline (local-intent-first, RP-INV-6).
- **`provisioning_operations`** — the idempotency ledger (an `in_progress` row older than `IDEMPOTENCY_IN_PROGRESS_LEASE` is reclaimed; pruned after 30 days by `ledger-prune`), keyed by the caller-supplied `Idempotency-Key` header (or an SQS envelope ID for consumer-driven operations).
- **`pending_audit_entries`** — durable hand-off of the non-bus `TenantIdpConfigChanged` audit entry to Audit Log's AL-5 direct-write ingest (`POST /api/v1/internal/audit-entries`, HLD §9.4, LLD §10.6/RP-D15); enqueued in the same `RunInTx` as the IdP-config write, drained by `cmd/server/audit_delivery.go`, deleted on delivery.
- **The Keycloak Admin API itself** — every mutation against Keycloak in the entire IAM subsystem goes through this service's `KeycloakAdmin` port, implemented by exactly one adapter using `Nerzal/gocloak`. No other IAM service, and no other package in this repo, may call Keycloak's admin endpoints directly — enforced in CI by `.github/scripts/arch-lint.sh` grepping every Go file for a stray `gocloak` import.

**Does NOT own:** the organizational/business model — tenants-as-business-entities, memberships, department/role grants, plan/subscription state (Org & Membership); credentials validation at request time or JWT issuance (Keycloak itself, at runtime); delegation, tender ACL overlays, or group→role mapping config (their own sibling services); any per-user table (there is none — Keycloak is the sole store of user identity/credentials); secret material of any kind in Postgres (realm passwords and trial-user seed credentials live only in Keycloak; IdP client secrets live only in OpenBao at `secret/data/iam/realm-provisioner/idp/<tenant_id>/<idp_alias>`).

**Two ordering disciplines, used per-flow (§9.1):**
1. **Keycloak-effect-first, then local commit** — the default for every provisioning/migration/IdP/MFA/realm-config-apply-success flow. The Keycloak mutation runs entirely outside any Postgres transaction; only on success does `RunInTx` commit the local row **and** enqueue the outbox event(s) atomically. A crash between the two is recovered by idempotent replay of the same `Idempotency-Key` — the Keycloak step becomes a no-op reconcile (already exists), then the local commit lands. A committed local row therefore always reflects a real Keycloak state, never the reverse.
2. **Local-intent-first, then reconcile** — used only for RP-8 realm-config when Keycloak is transiently unreachable: the desired value is recorded `pending` in `realm_config_reconciliations` and the caller gets `200 {applied:false, reconciling:true}` (not an error), and RP-C4 converges it later.

## Architecture

Clean Architecture — dependencies point inward; outer layers never import inner layers. Three composition roots ship from one Docker image: `cmd/server/main.go` (HTTP API + 3 SQS consumers + outbox runner), `cmd/reconciler/main.go` (CronJob dispatcher, `--job=<name>`) and `cmd/migrate/main.go` (the Helm pre-install/pre-upgrade migrate Job). Full directory tree, shared library dependencies (`platform-gincommon` v1.6.0, `platform-events/v2` v2.0.0, `platform-pgcommon/v2` v2.0.0 — all latest, incorporated like `iam-org-membership` — `Nerzal/gocloak` v13.9.0), RoutingPublisher-vs-single-topic wiring, and `go-arch-lint` dependency rules (including the two CI-enforced invariants beyond the layering check — RP-INV-1 and RLS-6) are in **[`.claude/architecture.md`](architecture.md)**.

## Data Model

Database `provisioner` on shared RDS PostgreSQL (Multi-AZ, PgBouncer transaction pooling in production); **6 tenant-scoped tables** under `FORCE ROW LEVEL SECURITY` (`tenant_realms`, `keycloak_idp_configs`, `keycloak_idp_config_validations`, `realm_config_reconciliations`, `provisioning_operations`, `pending_audit_entries` — the last two are RLS-scoped, unlike a typical ledger/queue, because their `result`/`entry` payloads embed tenant data), **3 RLS-exempt operational tables** (`outbox_events`, `processed_events`, `exporter_watermarks`), and **1 audit-only table with RLS deliberately disabled** (`rls_violation_log`, so its own writer function doesn't recurse into its own policy check). `record_version`-based optimistic locking on the two tables that carry it (`tenant_realms`, `keycloak_idp_configs`). Single consolidated migration `000000_initial_schema` (this service has never shipped a prior version). Full table catalogue, RLS invariants (Cases 1–5 + two structural tests), triggers, migration ordering, and the "data not stored here by design" list (no secrets, no per-user table, no tenant business-entity table) are in **[`.claude/database-schema.md`](database-schema.md)**.

## API, Caching & Events

One route prefix, `/api/v1/internal/*` — this service has almost no public surface; every route is mesh-internal (Signup BFF, Org & Membership, Billing via events, operator tooling). `/metrics` is served on a separate port, never on the main router. **17 endpoints** (RP-1..RP-17): 15 system-authenticated, 2 operator-only (RP-13 whole-estate IdP audit, RP-14 emergency suspend). Every mutating endpoint marked "required" enforces `RequireIdempotencyKey` against the `provisioning_operations` ledger — missing header is `400 missing_idempotency_key`, a reused key against an in-flight operation is `409 operation_in_progress` (a `failed` key, or an `in_progress` one past the 15m lease, is reclaimed and re-executed), a reused key against a `succeeded` operation replays the stored result rather than re-executing. One SNS topic (`iam-tenant-events`, **not** a `RoutingPublisher` like some siblings) carries all **9 produced events**; three separate inbound SQS queues (`membership-realm-q`, `tenant-realm-q`, `billing-realm-q`), each with its own consumer and `-dlq` sibling (`maxReceiveCount=5`), dedup via `processed_events`. Full endpoint catalogue, error taxonomy, event catalogue (produced + consumed), and AsyncAPI/schema-drift mechanics are in **[`.claude/api-caching-events.md`](api-caching-events.md)**.

## Request Flows, Concurrency & GDPR

Cross-cutting discipline: Keycloak-effect-first, then local commit (§9.1, see above) — visible in every method in `provisioning_service.go` and `lifecycle_service.go`. Compensating teardown on multi-step Keycloak sequence failure (`ProvisionDirect`, `Convert` — `bestEffortDeleteRealm`, itself idempotent). Full flows for trial provisioning (RP-1), direct-paid provisioning (RP-2, with least-loaded shard placement from the **local** mirror), trial→dedicated conversion with user migration (RP-3, `sub`-preserving, TOTP copied, WebAuthn re-enrollment flagged), revert-conversion (RP-4, within a fixed window), IdP configuration under the §11.6 gate (RP-6/7), realm-config local-intent-first (RP-8/RP-C4), MFA reset + role-sync reconcile (RP-9 + `membership-realm-q`), reactivate (RP-10), trial expiry (RP-12/RP-C1), operator suspend (RP-14), idempotent user delete/session-revoke (RP-15/16), trial hard-delete (RP-C2), and subscription lapse suspend→offboard (RP-C3) are all in **[`.claude/request-flows.md`](request-flows.md)**, along with the idempotency-ledger, consumer-dedup, and GDPR/data-lifecycle mechanics (PII scope, erasure via RP-C1/RP-C2/RP-C3, retention schedule).
