# Changelog

All notable changes to this service are documented here. Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versioning aligned with SemVer.

This service has never been deployed to any environment — there is no released version yet, so everything lives under `[Unreleased]`. Because of that, this file tracks only what is currently true and what is still outstanding, not a phase-by-phase build history; the full development diary is available via `git log` if it's ever needed.

## [Unreleased]

### Added

Initial build of the Realm Provisioner Service — the single writer to the Keycloak Admin API and system of record for tenant identity lifecycle (LLD `docs/lld/iam-lld-realm-provisioner-service.md`, v1.0 Approved).

- **HTTP API — 16 endpoints (RP-1..RP-16),** all under `/api/v1/internal`: `provision-trial`, `provision-direct`, `:id/convert`, `:id/revert-conversion`, `:id/users` (invite), `:id/idp` (PUT), `:id/idp/:alias` (DELETE), `:id/realm-config` (PATCH), `:id/users/:uid/mfa-reset`, `:id/reactivate`, `:id/realm` (GET), `:id/expire-trial`, `audit/idp-region-portability`, `:id/suspend`, `:id/users/:keycloak_user_id` (DELETE), `:id/users/:keycloak_user_id/revoke-sessions`.
- **Keycloak admin adapter** (`internal/adapter/outbound/keycloak/`) — the sole implementation of the `KeycloakAdmin` port (RP-INV-1 single-writer invariant, enforced in CI). Realm creation from template, OIDC client registration, user creation/migration/deletion, session revocation, MFA realm-role sync, IdP create/update/delete, realm enable/disable/export.
- **OpenBao adapter** (`internal/adapter/outbound/openbao/`) — Kubernetes-auth-backed KV v2 client for SAML/OIDC IdP secrets at the frozen path `secret/data/iam/realm-provisioner/idp/<tenant_id>/<idp_alias>`. No IdP secret material is ever persisted to Postgres.
- **Postgres schema** (`internal/adapter/outbound/postgres/migrations/`) — `tenant_realms`, `keycloak_idp_configs`, `keycloak_idp_config_validations`, `realm_config_reconciliations`, `provisioning_operations` (5 tenant-scoped tables, `FORCE ROW LEVEL SECURITY`); `outbox_events` (via `platform-events`' `outbox.ApplySchema`) and `processed_events` (RLS-exempt).
- **Transactional outbox + 9 produced events** on `iam-tenant-events`: `TrialTenantProvisioned`, `TenantRealmReady`, `TenantConverted`, `DirectPaidSignup`, `TrialExpired`, `TrialReactivated`, `TenantSuspended`, `TenantOffboarded`, `TenantReactivated`.
- **3 SQS consumers**: `membership-realm-q` (`DepartmentMembershipGranted`, `DepartmentMembershipLevelChanged`, `TenantRoleGranted`, `TenantRoleRevoked` → MFA realm-role sync), `tenant-realm-q` (`TrialStarted` → trial timer record), `billing-realm-q` (`TenantReactivated` → billing-driven reactivation). Wired through `platform-events` (`NewSQSConsumerWithClient`, Glue-decode codec, per-queue `WithConcurrency`). Deduped via the local `processed_events` ledger (`Envelope.ID` + `INSERT ON CONFLICT DO NOTHING` in the same `RunInTx` as the projection write — `platform-events` has no processed-events API; this matches `iam-org-membership`). Unknown event types are silently ack'd, counted, and marked processed so a producer adding a type cannot storm the queue.
- **6 reconciler jobs** (`cmd/reconciler`, dispatched via `--job=<name>`): `trial-expiry` and `trial-hard-delete` (RP-C1/RP-C2), `subscription-lapse` (RP-C3, two-phase suspend→offboard against O&M's I-16 `GET /api/v1/internal/subscription-lapses`), `realm-config-reconcile` (RP-C4), plus `outbox-prune` and `processed-events-prune` retention hygiene jobs.
- **`tenant_realms.suspension_source`** (`billing_lapse`|`operator`) — durable record of why a realm was suspended, backing RP-C3's offboard-phase retention query; set by RP-14 (`operator`) and RP-C3's suspend phase (`billing_lapse`), cleared by RP-10's reactivate.
- **Idempotency ledger** (`provisioning_operations`, keyed by the caller's `Idempotency-Key` header) and Keycloak-effect-first-then-local-commit ordering discipline (§9.1) with compensating teardown on partial multi-step failures (§9.3).
- **CI pipeline** (`.github/workflows/`) — `validate-test.yml` (unit/postgres-RLS/integration tests with race detector + coverage gate + arch-lint + e2e), `validate-quality.yml` (fmt/tidy/vet/lint/vuln-check/Dockerfile digest pinning), `ci.yml` (orchestration + single-image Docker build carrying both binaries + Trivy scan + Cosign signing), `changelog-check.yml`. Includes an AsyncAPI-vs-`internal/eventschema` drift test (`internal/eventschema/asyncapi_drift_test.go`) as this service's CI-enforceable substitute for a live Glue-registry comparison.
- **`release.yml`** — the tag-triggered release pipeline anticipated by `VERSIONING.md` § Maintainer release process (LLD §13.5), modeled on sibling `iam-authz-enrichment`'s release workflow and adapted for this service's two binaries and HTTP-only (no gRPC) health surface: `validate-test`/`validate-quality` re-run at the tag → `build` (tag/CHANGELOG verification, cross-compiled `iam-realm-provisioner-server`/`iam-realm-provisioner-reconciler` for 5 platforms) → `docker` (build/push/Trivy scan/SBOM/provenance/Cosign sign/smoke test both binaries) → `deploy-gate` (skipped unless `vars.DEPLOY_GATE_ENABLED=true`) → `publish` (GitHub Release). Adds `.github/scripts/verify-release-tag.sh`, `verify-changelog-entry.sh`, `prepare-release-binary.sh`, `export-image-provenance.sh`, `extract-release-notes.sh`, `create-github-release.sh`.
- **`freeze-watchdog.yml`** — daily cron guarding against a forgotten `SCHEMA_FREEZE` (staging/production) left active on `schema-registry.yml`, modeled on sibling `iam-user-profile`'s workflow of the same name.
- **Deploy manifests** (`deploy/`) — Helm chart (Deployment + CronJobs sharing one image), AWS IAM policy for SNS/SQS/Glue/S3/KMS, OpenBao policy + Kubernetes-auth role binding, Prometheus alert rules for the `iam_realm_provisioner_*` metric family, Keycloak realm template.
- **Schema governance pipeline** (`make schema-*`, `.github/workflows/schema-registry.yml`, `schema-prune.yml`, `schema-health-quarterly.yml`, `deploy/monitoring/schema-registry-alerts.yml`, `docs/runbook-schema-registry.md`) — the `platform-schemagov` CLI (Docker image, no Go-code presence) now drives full registration/diff/prune/health governance of this service's 9 event schemas on the shared `iam-tenant-events` Glue registry, on top of the pre-existing drift gate (now `schema-registry.yml`'s `pr-check` job, not `validate-quality.yml`). The pipeline is built shared-registry-aware from day one: it never registers, diffs, verifies, or prunes `iam-org-membership`'s `TenantCreated`/`TrialStarted` schemas on that same registry, and `schema-prune.yml` hard-blocks its `--execute` path whenever either name is present (the underlying CLI has no name-exclusion flag). Usage-based lifecycle auto-deprecation (`enforce-lifecycle`) ships wired but dormant — `PROMETHEUS_URL` is deliberately left unset because this service is pre-production and its 9 events are frozen (LLD §25); it activates once a real production Prometheus exists.
- **`rls_violations_total` metric + two RLS-6 alerts** (`IAMRealmProvisionerRLSCrossTenantAccess` critical, `IAMRealmProvisionerRLSMissingGUC` warning, in both `deploy/helm/templates/prometheusrule.yaml` and `deploy/monitoring/app-alerts.yml`) — a fourth exporter goroutine in `cmd/server/exporters.go` (`GaugeRepository.RLSViolationCounts`) scrapes `rls_violation_log` on a persisted high-water mark (new `exporter_watermarks` table, §4.2), not a fixed trailing window — the mark, shared by every server replica via `SELECT ... FOR UPDATE`, is what makes a pod restart or another concurrent HPA replica's tick never re-count a violation already tallied. Needs a Terraform-side `GRANT SELECT ON rls_violation_log` and `GRANT SELECT, INSERT, UPDATE ON exporter_watermarks TO realm_provisioner_migrator` this repo cannot itself provide — see Known gaps.
- **Idempotency ledger (`provisioning_operations`) reclaims a `failed` row instead of poisoning that key forever.** `IdempotencyRepository.Begin`'s `ON CONFLICT DO NOTHING` previously treated any existing row — including one left `failed` by a single transient error — as "already handled," so `idempotency_key`'s `PRIMARY KEY` plus no cleanup job for that table meant one Keycloak/S3 hiccup permanently 409'd (HTTP) or silently no-op'd-as-success (RP-C1/RP-C3 reconciler jobs) every future retry of the same key, exactly contradicting `Fail`'s own doc comment and every `409`'s "previously failed — retry" message. `Begin` now does `ON CONFLICT DO UPDATE ... WHERE status = 'failed'`, atomically resetting a failed row to `in_progress` so the caller actually proceeds; a `succeeded` or genuinely `in_progress` row is untouched, exactly as before.
- **`Convert` (RP-3) no longer destroys already-migrated users on a later user's migration failure.** `MigrateUser` deletes each user from the source (shared) realm before creating it in the target (dedicated) realm, so once at least one user in the loop has been migrated, that user exists nowhere else — `bestEffortDeleteRealm`'s prior blind "tear down the new realm on any failure" behavior was permanent, unrecoverable data loss for every user already moved earlier in the same loop. `Convert` now tracks whether the target realm may already hold migrated users and skips teardown once it does; a retry with the same `Idempotency-Key` resumes against the existing (deterministically-named) realm — tolerating `CreateRealmFromTemplate`'s `ErrRealmAlreadyDedicated` conflict as proof of its own earlier partial attempt — and a fresh `ListUsersByTenant` naturally picks up only whatever remains in the shared realm.
- **Keycloak adapter transport now actually retries on 5xx/429/timeout**, closing the gap where `.claude/CLAUDE.md`/`ARCHITECTURE.md` already documented "bounded exponential-backoff retry ... 429 honours Retry-After" but no such retry existed. A new `retryTransport` (outermost layer of `admin.go`'s transport chain, so tracing and 401-driven token invalidation still wrap every individual attempt) retries up to `retryMaxAttempts` (4) with full-jitter exponential backoff (`retryBaseDelay` 200ms, capped at `retryMaxDelay` 5s), honoring a 429's `Retry-After` (integer-seconds or HTTP-date). Safe as a blind retry because every mutating call already has a natural conflict-detector for "the request actually succeeded, the response was lost" (username/email uniqueness, `partialImportUser`'s `ifResourceExists=FAIL`, `CreateRealm`'s 409).
- **RP-6 (`ConfigureIdp`) is now actually ledgered against its required `Idempotency-Key`.** The route has always enforced `RequireIdempotencyKey`, but the service never called the idempotency store — a retry re-ran the entire flow (re-validating, re-recording an audit row, re-writing OpenBao, re-calling Keycloak) instead of replaying the stored result. `ConfigureIdp` now does the same `Begin`/`Complete`/`Fail` dance as every other mutating RP endpoint. It also adds a compensating OpenBao-secret delete when `CreateOrUpdateIdp` fails after the secret was already written — but only when this alias had no prior config (confirmed via `FindByAlias`); an update to an already-configured alias never deletes on failure, since the pre-existing Keycloak IdP is still live and unaffected by the failed update.
- **RP-C4 realm-config reconciler now has a poison-pill cap.** `MarkFailed` previously always left a row `pending` regardless of `attempts`, so a permanently-broken setting (e.g. a deleted realm, a since-invalid desired value) retried every 10-minute tick forever, indefinitely occupying a `ListPending` batch slot. `MarkFailed` now atomically moves a row to the (already-defined-but-previously-unused) terminal `failed` `recon_status` once its attempt count reaches `RECONCILER_MAX_ATTEMPTS` (new env var, default 20 — ~3.3 hours of retry at the `*/10 * * * *` schedule).
- **`/readyz`'s 4 dependency checks (database, sys_database, outbox, Keycloak) now run concurrently** instead of sequentially, so one slow-but-healthy dependency can no longer consume the whole readinessProbe timeout budget before a later check even starts.
- **`outboxPrune`/`processedEventsPrune` CronJobs' `activeDeadlineSeconds` raised from 300s to 360s** — equal to (not exceeding) `RECONCILER_TIMEOUT`'s default 300s, the same footgun already fixed for `realmConfigReconcile`: Kubernetes would hard-kill the Job before the app's own internal context deadline could ever fire.
- **`MigrateUser`'s source-user delete is now retry-safe.** It called the raw gocloak `DeleteUser` directly instead of the `isNotFound`-tolerant pattern every sibling delete in the same file already uses — with `retryTransport` now in the chain, a DELETE that actually succeeded but whose response was lost would be transparently retried, land on an already-deleted user, get a 404, and `MigrateUser` would hard-fail on it — after the source user was already gone and never created in the target. Permanent, silent data loss for exactly the call this session's `Convert` fix was built to make recoverable. Now tolerates a 404 the same way every other delete in `admin_users.go` does.
- **`Convert`'s (RP-3) dedicated-realm name now uses the full tenant UUID, not an 8-hex-char (32-bit) prefix.** The retry-resume logic added this session treats a `CreateRealmFromTemplate` name conflict as proof of "my own earlier partial attempt" and resumes against the existing realm — safe only if that name is actually unique to this tenant. An 8-hex-char prefix carries just 32 bits of collision resistance; at large-enough dedicated-tenant counts, two different tenants could collide onto the same name, and the second tenant's users would be migrated into the first tenant's realm — a tenant-isolation violation. Now uses the full UUID (128 bits), matching the collision-resistance this service already assumes elsewhere for tenant-id uniqueness.
- **`retryTransport`'s `Retry-After` seconds-form no longer risks an int64 overflow.** An oversized (or hostile) `Retry-After: <huge integer>` value could overflow the `* time.Second` conversion into a negative duration, which bypassed the `retryMaxDelay` cap and fired an immediate retry instead of the requested backoff. Now clamped to the largest representable `time.Duration` in seconds before the multiply.
- **`validateRequiredEnv`'s "or holds a dev-default value outside `APP_ENV=dev`" fail-fast — documented in `.claude/operations.md` since this service's initial build — now actually exists in code.** Every check there previously only looked for *emptiness*; a dev `.env` pasted verbatim into a staging/production secret would start the service cleanly and fail confusingly at the first real Keycloak/O&M call instead of panicking at boot. `validateRequiredEnv` now also rejects `KEYCLOAK_BASE_URL` / `KEYCLOAK_ADMIN_CLIENT_SECRET` / `ORG_MEMBERSHIP_BASE_URL` holding their literal `.env-example` placeholder value outside `APP_ENV=dev`.

- **`idp_alias` is now validated against a strict allow-list (`^[a-zA-Z0-9_-]{1,64}$`) before RP-6/RP-7 ever touch OpenBao or Keycloak.** `openbao.Client.idpPath` builds `"<prefix>/<tenant_id>/<idp_alias>"` via plain string interpolation with no sanitization at that layer, and `idp_alias` flowed there unvalidated all the way from RP-6's JSON body and RP-7's URL path param — no format constraint existed anywhere in the stack (HTTP binding, domain, or DB schema). A caller-supplied alias containing a path-traversal sequence (e.g. `"../<other-tenant-id>/evil"`) could have resolved outside the intended tenant-scoped OpenBao path. The new validation forbids dots entirely, so `.`/`..` can never appear as a path component; enforced in `IdpService.ConfigureIdp`/`RemoveIdp` — the single choke point both RP-6 and RP-7 share — before any downstream call, with tests proving rejection both at the service layer and end-to-end through the real router.
- **`ResetMFA` (RP-9) no longer accumulates duplicate `CONFIGURE_TOTP` entries in Keycloak's `requiredActions` on a repeated reset.** RP-9 carries no idempotency ledger by design (fail-closed, no reconciler), so a second admin-triggered reset for the same user previously appended a second `CONFIGURE_TOTP` regardless of whether one was already present — unbounded, dirty state growth over repeated resets. Now dedups against an existing entry before appending.

- **Dockerfile base images are now actually digest-pinned.** `validate-quality.yml`'s own "Dockerfile base image digest check" gate greps for an unpinned `FROM image:tag` line and fails CI if it finds one — both `FROM` lines (`golang:1.26.6-bookworm`, `gcr.io/distroless/static-debian12:nonroot`) matched that pattern exactly, meaning this gate would have failed on every CI run against the current Dockerfile despite the repo's own documented supply-chain guarantee. Both now pinned to their resolved `@sha256:...` digests.
- **The Keycloak client-side rate limiter now covers `retryTransport`'s retries, not just each outer Admin method's first attempt.** `Admin.token` previously called `rateLimiter.Wait` once per method invocation, before the actual HTTP request(s) that method makes — but those requests go through `retryTransport`, which can silently retry the *same* request up to `retryMaxAttempts` (4) times on 5xx/429/timeout with zero rate-limiter involvement. A burst of concurrent Admin calls throttled to `KEYCLOAK_RATE_LIMIT_RPS` at the token layer could still generate up to ~4x that many actual requests per second during a retry storm — precisely when Keycloak is already struggling and the rate limiter matters most; a real resilience gap introduced by this session's retry infrastructure. Moved rate-limiting into a new `rateLimitTransport`, positioned as `retryTransport`'s base in `admin.go`'s transport chain, so every actual outbound HTTP request — including each retry — is throttled. As a side benefit this is also more precise than before: a token-cache hit (no network call) no longer consumes rate-limit budget it never used.
- **`BillingConsumer`'s billing-driven reactivation now clears `suspension_source`, matching RP-10's own `Reactivate` path.** Previously left stale after a billing-lapse reactivation via the `billing-realm-q` consumer (unlike `LifecycleService.Reactivate`, which explicitly clears it) — a data-hygiene asymmetry between the two reactivation code paths with no observed functional consequence today, but inconsistent with the invariant every other suspend/reactivate path maintains.

- **`RevertConversion` (RP-4) no longer permanently strands a tenant when the dedicated realm is deleted but the local commit fails.** `DeleteRealmIfExists` ran unwrapped as the last Keycloak step before `tx.RunInTx` committed the local row (Strategy→shared); if the delete succeeded but the commit failed (an ordinary DB hiccup), the local row was left pointing at a dedicated realm that no longer existed. Every retry with the same Idempotency-Key re-fetched that stale row and called `ListUsersByTenant` against the now-nonexistent realm, which had no not-found tolerance and hard-failed every time — the tenant was stuck, unable to revert or convert, until an operator manually corrected the row. `Admin.ListUsersByTenant` now surfaces a distinguishable `ErrTenantRealmNotFound` on a 404 (reliable here — a realm that exists but matches zero users returns 200 with an empty list, never 404) instead of the generic `ErrKeycloakUnavailable`; `RevertConversion` treats that specifically as proof of an earlier attempt's already-completed migration-and-delete, and resumes straight to the local commit instead of re-attempting (or getting stuck re-failing) against the absent realm.
- **§11.6 check 5 (`CheckSLOResponseRegion`) was a byte-for-byte duplicate of check 2 (`CheckSLOURLRegion`) — same field, same condition — and never independently validated anything.** The LLD documents checks 4-6 as a distinct group (ACS/SLO-response/EntityID pointing at the region-neutral host), but check 5's implementation just re-ran check 2's `slo_url` substring check under a different check ID. Now examines a distinct `slo_response_url` config key (SAML's `SingleLogoutService` `ResponseLocation`, which per spec defaults to `Location`/`slo_url` when a caller never sets it — preserving identical behavior for every existing caller) — a caller who *does* supply a distinct region-pinned response URL is now correctly caught, closing a real (if narrow, given no caller currently populates this field) gap in a security/compliance-relevant gate. Also fixed a stale doc comment omitting check 3 from the CRITICAL-checks list in both `idp_validation.go` and `idp_validator.go`.
- **A lost-response retry on user creation (RP-1's trial user, RP-5's `CreateInvitedUser`, RP-2's invited-user step) can now be resolved automatically instead of permanently stranding an idempotency key.** `retryTransport` never retries a 409 itself, but a caller retrying the same `Idempotency-Key` after a network blip could previously get stuck: the original `CreateUser` had actually succeeded, but the retry's 409 (Keycloak's email-uniqueness constraint) was indistinguishable from a genuine conflict — both folded into the generic `ErrKeycloakUnavailable`. `CreateTrialUser`/`CreateInvitedUser` now surface a 409 as the distinguishable `ErrUserEmailConflict`, and a new `KeycloakAdmin.FindUserByEmail` port method (exact-match lookup, returning the existing user's id + `tenant_id` attribute) lets `provisioning_service.go`'s new `resolveUserCreateConflict` helper tell "this is my own earlier attempt" (existing user's `tenant_id` matches the retried request — resume with that user's id, no failure at all) apart from "a different tenant genuinely holds this email" (the original conflict propagates unchanged, idempotency key marked failed). `ProvisionDirect`'s resolution runs *before* its compensating realm-delete-and-recreate, so a resolved same-tenant conflict no longer wastefully tears down and rebuilds a perfectly good dedicated realm + OIDC clients just to dodge its own already-created user.
- **`wrapConnErr` (`internal/adapter/outbound/postgres/db.go`) no longer masks a caller's own business-rule error as a generic 503 `db_unavailable`.** Its final fallback branch converted *any* error it couldn't positively classify — including a plain Go error a service intentionally returns from inside `RunInTx`/`withPool` to trigger a rollback — into `ErrDBUnavailable`, discarding the real error entirely. This broke `RunInTx`'s documented rollback contract outright (`errors.Is(returnedErr, originalErr)` never held) and was surfaced by `make test-ci`: `TestTxRunner`, `TestProcessedEventsRepository`'s rollback cases, and a stale unit test that had encoded the bug as expected behavior. Now passes through any error it can't positively identify as a genuine connectivity/resource failure unchanged; the one additional positive case added is `puddle.ErrClosedPool` (surfaced by `pgxpool.Pool.BeginTx`/`Acquire` on a closed pool — a real connectivity failure that was previously only caught by this same over-broad fallback, verified against a real closed-pool integration test). Also fixed an unrelated, pre-existing test-isolation race in `processed_events_store_test.go`: `CleanupExpired` and `Prune` both sweep the same unscoped, non-tenant-scoped global `processed_events` table and were running as parallel siblings, letting one test's TTL sweep consume the other's just-inserted rows.

- **A Swagger UI is now mounted at `GET /swagger/*any`, alongside the existing AsyncAPI viewer.** All 16 RP-1..RP-16 handlers carry `@Summary`/`@Router` swag annotations (plus global API metadata in `cmd/server/swagger_info.go`); `make swag` generates the checked-in `docs/swagger/{docs.go,swagger.json,swagger.yaml}`, blank-imported by `cmd/server/main.go` to self-register at init. Custom-themed via `SwaggerThemeHandler`/`SwaggerInitializerHandler`, gated identically to `/asyncapi` (`DocsConfig.active()`, optional bearer token in production). Found and fixed alongside this: `docs/swagger/` was already stale relative to the annotations it was generated from (RP-2's `@Success` said `201` but the committed spec said `200`; `GetRealmResult`'s new `record_version` field was missing entirely) — regenerated and verified `make swag-check` (its previously-missing backing script, `.github/scripts/check-swagger-stale.sh`, was added — matches `iam-org-membership`'s identical script: `make swag` in place, then `git diff --quiet -- docs/swagger/`).
- **Bug fixes found during API testing, lifecycle/IdP services (`lifecycle_service.go`, `idp_service.go`):** `ExpireTrial` (RP-12) now rejects a dedicated-strategy tenant with `409 realm_already_dedicated` (was `400`) and a suspended tenant with `409 tenant_offboarded` (previously returned `200`, silently no-opping trial-expiry bookkeeping against a tenant a billing-lapse or operator suspension had already taken out of the trial lifecycle). `Reactivate` (RP-10) now rejects a still-`provisioning` tenant with `409 tenant_offboarded` (previously `200`, reactivating a tenant that never reached `active`) and defaults a nil `new_trial_ends_at` to +30 days instead of leaving it empty (was failing `TrialReactivated`'s event-schema validation with an empty-string date). `GetRealmResult` (RP-11) now includes `record_version`, previously missing from the response entirely. `ConfigureIdp` (RP-6) checks `offboarded` before the dedicated-realm check (previously reached Keycloak for an offboarded tenant). `RemoveIdp` (RP-7) now checks the tenant realm and `keycloak_idp_configs` row exist (`404 tenant_realm_not_found`/`404 idp_config_not_found`) before calling Keycloak's delete, and makes the OpenBao secret delete explicitly best-effort (log-and-continue). The §11.6 IdP Configuration Checklist gained three CRITICAL checks: `check_0_config_safe` (rejects an HTML/XML injection sequence in any config value), `check_14_oidc_client_id` (OIDC `client_id` required), `check_15_oidc_issuer_https` (OIDC `issuer` must be a non-empty, valid HTTPS URL) — now 12 CRITICAL / 4 WARN, 16 checks total (was 9/4/13).
- **`api/asyncapi.yaml` aligned with `iam-org-membership`'s spec structure** — added `info.license`, `defaultContentType`, `components.tags` (published/consumed, applied to all 15 messages), `components.securitySchemes.iamRole`, and `components.messageTraits.glueWireFormat` (applied to all 15 messages). The `/asyncapi` viewer was replaced with an interactive dashboard (searchable, dark/light theme, deep-linkable schema fields) ported from `iam-org-membership`'s equivalent viewer, powered directly by the new published/consumed tags.
- **A cross-repo field-name mismatch was silently defeating part of the RP-9/`membership-realm-q` residual-MFA check.** `orgmembership.Client`'s `membershipProjection` struct expected O&M's I-8 department-level field as JSON key `level`, but O&M's actual `DeptMembershipView` serializes it as `role_level` — every department entry silently decoded to an empty `Level`, so `HasResidualMFARequirement` could never detect a residual MFA requirement sourced from a `reviewer`/`approver` department membership on the `TenantRoleRevoked` MFA-drop path (only the role-based `tenant_owner`/`tenant_admin` check still worked). The existing tests encoded the same wrong field name in their mock responses, so they passed despite the bug. Fixed the struct tag; added a regression test asserting a payload keyed `level` (the old, wrong name) is never read as a residual requirement.
- **A lost-response retry landing on `resolveUserCreateConflict` with an unset `TenantID` (`uuid.Nil` — never expected from real request binding, but not actually prevented by it) could match an unrelated attribute-less legacy Keycloak user by pure zero-value coincidence** (both sides `uuid.Nil`), handing back that stranger's Keycloak id as if newly created for a non-existent tenant. The function's own doc comment already claimed this case "never equals a real tenant id," but the code had no such guard. Added the explicit `uuid.Nil` short-circuit plus a regression test proving `FindUserByEmail` is never even called in this case.
- **`schema-registry.yml`'s diff/register steps were computing the wrong Glue schema name, silently skipping the breaking-change gate on every run.** The `staging`, `production`, and `pr-check` jobs (and the local `make schema-register` target) pointed `--schema-dir`/`--proposed` directly at `internal/eventschema/`'s snake_case filenames (`trial_tenant_provisioned.json`) and derived `SCHEMA_NAME` from that raw filename — but AWS Glue's real registered name is PascalCase (`TrialTenantProvisioned`, matching `eventschema.ByEventType`, LLD §25, `api/asyncapi.yaml`). A snake_case `SCHEMA_NAME` made `aws glue get-schema` always report "not in registry" even for an already-registered schema, so the diff step's breaking-change detection never actually ran — confirmed by comparing against `iam-org-membership`'s identical pipeline, which stages first for exactly this reason. Added `.github/scripts/stage-produced-event-schemas.sh` (copies the 9 files into `.tmp/glue-schemas/<PascalCaseName>.json`, matching O&M's identically-named script) and wired a staging step before every diff/register step in all three jobs, plus the equivalent `make schema-register` fix. `validate`/`extract-schemas` were unaffected — they never needed the Glue name.
- **`ci.yml` split into parallel `build-image`/`trivy`/`smoke` jobs, matching `iam-org-membership`'s pipeline.** Previously one job ran Hadolint → build+load → Trivy scan → smoke tests (×2, this service's two binaries) → conditional push/sign steps sequentially. Now `build-image` is cache-only (no local load, no push, no longer gated on `validate-test` — starts immediately like O&M's) and feeds `trivy` and `smoke`, which run in parallel, each restoring the near-instant GHA cache hit. `trivy` gained a CycloneDX SBOM generation + artifact-upload step this service never had before. `pr-summary` now posts/updates an actual PR comment (`.github/scripts/pr-summary.js`, ported from O&M with RP's real 80% coverage threshold) instead of a bare `$GITHUB_STEP_SUMMARY` echo. `push` is now a dedicated job (needs `validate-test`+`trivy`+`smoke`+`validate-quality`) replacing both the old if-gated push steps and the separate `push-gate` no-op summary job — `push`'s own success is the gate.
- **`deploy/` Helm chart aligned with `iam-org-membership`'s conventions.** Chart de-nested from `deploy/helm/iam-realm-provisioner/` to `deploy/helm/` directly (git-tracked as renames, all 22 cross-references updated, verified with `helm lint`/`helm template` before and after). `values.yaml` keys renamed to match O&M: `service.httpPort` → `service.port`, `cronJobs:` → `cronjobs:`. `Chart.yaml` gained `kubeVersion: ">=1.28.0"` and a maintainer `email`, both present in O&M's but missing here. ### Known gaps

- **OpenBao integration** has been structurally reviewed and unit-tested, but never exercised against a live OpenBao instance — the Kubernetes ServiceAccount token file the auth flow depends on only exists inside a real cluster. RP-6/RP-7 will return `500` in any local-dev environment that attempts an IdP secret write/delete without a real OpenBao + Kubernetes auth binding.
- `failing_tenants` in the RP-13 audit response serializes as `null` rather than `[]` when the audit finds zero failing tenants — cosmetic, not yet fixed.
- **`rls_violations_total`'s exporter has no production grant yet.** `realm_provisioner_migrator`'s privileges are entirely Terraform-provisioned outside this repo; until that Terraform adds `GRANT SELECT ON rls_violation_log` and `GRANT SELECT, INSERT, UPDATE ON exporter_watermarks`, the exporter fails every 5-minute tick with a permission-denied error (logged at WARN, non-fatal) and both RLS-6 alerts stay dark. `test/postgres/syspool_helper_test.go` grants both directly for the test suite only.
